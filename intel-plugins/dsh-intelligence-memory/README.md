# Long-term memory persistence

English | [中文](README.zh.md)

The memory plugin stores original rows and a derived FTS5 index in its configured `dataDir/memory.db`. The retriever inserts both in one named savepoint. A failed index insert rolls back that memory write; an enclosing caller transaction retains its own changes and controls the final commit. The search joins existing memory rows before applying its result limit, while orphan index rows can still distort corpus ranking.

Native `memory_write` results persist `presentationMeta.memoryWrite` with `{ok:true,id}` after a successful write, or `{ok:false}` after a returned failure. The ID is the actual stored row ID. Upkeep uses this metadata with matching tool-call, turn and step identities to confirm a completed run; it does not infer write success from rendered text. This optional result metadata uses the existing Session event format.

The operator-only [maintenance module](src/maintenance.js) runs on Linux with the deployed Node runtime. `node src/maintenance.js inspect /absolute/memory.db` opens the existing database read-only and reports row, orphan, missing and mismatched index counts without memory content. `node src/maintenance.js repair /absolute/memory.db /absolute/unused-backup.db` requires quiescent writers and creates a private SQLite snapshot before modifying the derived index. It preserves every original memory field, rebuilds FTS rows using the same Chinese segmentation as normal writes, and returns before/after counts and hashes of the supplied backup path, snapshot and original memory rows. The caller already knows the backup path; the receipt does not echo it. Failure rolls back index mutations. It neither deletes memories nor invents replacements.

Back up the configured database, not an assumed default directory. Keep backups in a private directory and inspect the receipt before resuming writers. A historical full database snapshot must not overwrite later memory writes during rollback; rebuild the index from the current original rows instead. Maintenance does not establish retrieval quality, memory correctness or a long-term retention policy. [SQLite savepoint semantics](https://www.sqlite.org/lang_savepoint.html) and the [Node SQLite backup API](https://nodejs.org/docs/latest-v24.x/api/sqlite.html#sqlitebackupsource-db-path-options) define the transaction and snapshot behavior.

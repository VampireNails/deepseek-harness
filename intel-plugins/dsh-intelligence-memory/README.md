# Long-term memory persistence

English | [中文](README.zh.md)

The memory plugin stores original rows and a derived FTS5 index in its configured `dataDir/memory.db`. The retriever inserts both in one named savepoint. A failed index insert rolls back that memory write; an enclosing caller transaction retains its own changes and controls the final commit. Default reads, search and automatic recall exclude invalidated rows before applying the result limit. Orphan index rows can still distort corpus ranking.

Search preserves later subjects in conversational questions. `maxQueryChars` (default 65536 UTF-16 code units) bounds the raw input, and `maxQueryTerms` (default 2048 distinct Han characters and ASCII words) bounds both the input and synonym-expanded query. Exceeding either bound fails with `MEMORY_QUERY_TOO_LARGE` before SQLite. Terms are quoted literal OR operands. Common English conversational words are omitted when another subject exists; a literal query such as `for` remains searchable. `synonymGroups` defaults to preference, responsibility, reply and approval vocabularies; operators can configure at most 16 groups of 2–16 literal terms, each 1–32 Han/ASCII letters, digits or spaces.

The retriever scores adjacent Han pairs, whole ASCII words, single-Han queries and matched synonym concepts. IDF counts distinct matching-evidence patterns, so repeated logs cannot inflate the frequency of one pattern. `minimumScoreRatio` (default 0.1) removes candidates below that share of the best score; `duplicatePatternPenalty` (default 0.1) reduces each subsequent selection with the same evidence pattern by that share of the best score. Both are configurable finite ratios from 0 to 1. BM25 order breaks ties. Narrow Chinese personal-preference questions select literal personal statements before the candidate limit; preference-setting field names and ordinary factual requests stay in general search. This lexical heuristic does not infer unstated preferences or guarantee semantic recall.

`maxCandidates` (default 128) bounds one total SQL candidate window, and `maxCandidateBytes` (default 1048576) bounds the aggregate UTF-8 original text before any candidate text is fetched. Both are configurable positive safe integers. Byte overflow fails with `MEMORY_RECALL_TOO_LARGE`; use a more specific query or deliberately raise the bound. Automatic recall skips either size failure and emits a warning without query or memory text, subject to logger export settings; explicit search returns a native tool error. Search never truncates stored originals or silently drops oversized candidates. The bounded BM25 window can still omit relevant rows in a large heterogeneous corpus.

Native `memory_write` results persist `presentationMeta.memoryWrite` with `{ok:true,id}` after a successful write, or `{ok:false}` after a returned failure. The ID is the actual stored row ID. Upkeep uses this metadata with matching tool-call, turn and step identities to confirm a completed run; it does not infer write success from rendered text. This optional result metadata uses the existing Session event format.

Validity schema version 1 adds separate `memory_state` and append-only `memory_audit` tables; correction never overwrites or deletes an original memory. `memory_history` explicitly reads the full original, current revision and latest 50 audit entries, including invalidated rows. `memory_invalidate` and `memory_restore` require a reason and the read revision, and ask through the native tool approval service with the full original text. Missing agents or approval channels, refusal, cancellation and stale revisions prevent mutation. State, FTS and audit share a savepoint; restoration indexes the original text. New Feed/Artifact references require active memories with either the mounted authority or the read-only database fallback; historical publications remain readable.

The mounted `memoryManagement` service supplies bounded lists, explicit details and paired-client corrections. The phone authenticates through its existing pairing and confirms full text plus a reason before submitting; model calls require native approval instead. Audit source and session identity come from trusted execution context. Mutations bind a UUID to the arguments and actor: same-request retries return the recorded result without another audit, even after a later restoration; a reused UUID with different arguments fails. A revision conflict requires rereading. Losing a response or closing a window cannot undo a committed correction. Lists expose 240-character previews; details retain full originals, and the phone gateway declines originals above its 524288-character display bound.

The operator-only [maintenance module](src/maintenance.js) runs on Linux with the deployed Node runtime. `node src/maintenance.js inspect /absolute/memory.db` reports original and indexed rows plus orphan, missing, mismatched, invalidated-memory and invalidated-index counts without memory content. `node src/maintenance.js repair /absolute/memory.db /absolute/unused-backup.db` requires quiescent writers and creates a private SQLite snapshot before modifying the derived index. It preserves original fields, validity and audit, and rebuilds only active FTS rows using normal Chinese segmentation. Receipts contain before/after counts and hashes of the supplied backup path, snapshot and original rows without echoing paths. Failure rolls back index mutations.

Fresh databases initialize validity schema; existing databases remain readable without implicit preparation and do not advertise correction. With writers stopped, `node src/maintenance.js prepare-validity /absolute/memory.db /absolute/unused-backup.db` creates a private backup before the schema transaction, verifies unchanged original rows and retains the backup on failure. Reopen the plugin after preparation. Unknown or incomplete validity schemas fail closed. Source versions that do not understand validity must not run against a prepared store: they can recall invalidated originals. Reverting to such versions is not a supported rollback.

Back up the configured database, not an assumed default directory. Keep backups in a private directory and inspect the receipt before resuming writers. A historical full database snapshot must not overwrite later memory writes during rollback; rebuild the index from the current original rows instead. Maintenance does not establish retrieval quality, memory correctness or a long-term retention policy. [SQLite savepoint semantics](https://www.sqlite.org/lang_savepoint.html) and the [Node SQLite backup API](https://nodejs.org/docs/latest-v24.x/api/sqlite.html#sqlitebackupsource-db-path-options) define the transaction and snapshot behavior.

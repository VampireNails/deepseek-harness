# JobLog

English | [中文](README.zh.md)

JobLog stores completed runs in `intel-joblog/job_history.sqlite`, using Node's built-in SQLite. Each completion has a stable `runId`, task ID, scope, UTC finish time, optional start time, status, diagnostic detail and summary. `historyLimit` defaults to 200 completed runs per scope and accepts integers 1–1000. Newest completions appear first; fail → fail → ok retains both failures until retention evicts them. This bounded history does not establish a lifetime success rate. Latest states remain in `job_runs.json` / `job_test_runs.json`; `job_alerts.md` retains failures and `jobs.log` retains at most 2000 wrapper lines. The process audit remains in `route-runs.jsonl`.

New records carry explicit `production` or `test` scope. `JobLog(dir, { scope: 'test' })` and plugin `testRecords: true` select tests; ordinary writers default to production. Test latest states remain separate, so the same task name cannot replace production. `readHistory()` and the tools select production by default; `includeTests: true` explicitly includes tests and unclassified old snapshots. `readRuns()` retains its compatible latest projection. Task names never determine scope. Old records keep their source and original dates; before a legacy latest entry is overwritten, its exact snapshot is retained separately without inventing a run ID or reconstructing older runs. Reading and filtering never rewrite source files, and this feature does not migrate production data during installation.

The shared SQLite writer lock serializes writers with a three-second busy wait; the history database waits up to five seconds. A repeated `(scope, runId)` completion within retained history counts once; conflicting task/status/detail rejects. A late duplicate cannot replace a newer latest state. History commits before latest JSON is atomically renamed and fsynced, while the writer lock remains held. A failed commit cannot advance a compatibility file. Committed SQLite records remain authoritative if a later compatibility write fails; the caller receives a storage error with `committed: true`, rather than persisted-success acknowledgement. Corrupt or unreadable state rejects rather than becoming an empty successful view. Every log, completion and alert write failure throws a safe `JOBLOG_*` code with operation and safe errno where available. A task failure plus storage failure carries the original `taskError` and `persistenceCode`; storage errors never change a completed task's status. A persistence error can follow partial effects: inspect the run ID before retrying the task.

Trusted runner diagnostics retain at most 2048 characters, with a 200-character summary and `detailTruncated` flag; common credential/prompt fields are redacted. `guarded()` persists only completion/failure classification and a safe error code, never arbitrary returned text or error-message bodies; its caller still receives the original result/error. Alert details are indented so text cannot introduce a scoped header. Tool alerts default to explicitly marked production blocks; all-source reads preserve unknown old blocks. The compatible `selectAlerts()` default retains unclassified alerts unless `productionOnly: true` is requested. Missing alerts yield an empty view; other read failures reject without disclosing paths. An empty selection is not evidence that every task succeeded.

Back up the SQLite database together with all latest/log/alert files while writers are stopped. Earlier readers see latest states and retained alerts, but cannot display the new run history. Retention deduplication is bounded by retained runs; evicted IDs are not an eternal idempotency registry. Source scope comes from explicit writer metadata, never a task name. No task definitions, pairings, legacy sources or production records are reclassified or cleared.

Run `node --test intel-plugins/dsh-intelligence-joblog/tests/*.test.js` on Linux. The owning fixtures use temporary directories and no production Host or models.
